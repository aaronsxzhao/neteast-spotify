# 代码更新必须有对应安装包

## 自动发布

维护仓库 `aaronsxzhao/neteast-spotify` 的 `main` 每次 push 触发 `.github/workflows/release-macos.yml`，也可在 Actions 手动运行。状态分支和朋友的部署仓库不触发打包。快速连续推送时，GitHub 可合并等待中的构建；只发布仍对应 main 最新提交的产物。

流水线依次执行：

1. 在标准 macOS 14 arm64 runner 安装 Node 22 与锁定依赖。
2. 完整回归测试。
3. 生成与朋友部署完全相同的文件树，在临时隔离目录运行云端测试。相对模块缺失直接失败；不靠开发目录补齐文件。
4. 下载并校验官方 GitHub CLI，准备 Node/CLI 许可证。
5. 打包当前提交，内置 `build-info.json`（版本、源码 SHA、架构和构建时间）。使用包内 Node 验证网易云依赖、离线 QR 渲染、云端文件树和空白账号页面。
6. 校验 ZIP 的 SHA-256，以草稿上传 ZIP 与校验文件，上传成功才公开 Release。默认仍为未公证内测版。

版本来自 package.json 加 `-build.<run_number>.<run_attempt>`；每次重跑版本不同，不覆盖既有包。版本不再硬编码为 beta.2。Release 说明、安装器界面和云端 `daily-relay-build.json` 可追溯源码与部署内容摘要。

发布任务不使用音乐 Secrets、不运行音乐同步、不改每日同步 workflow。仅发布步骤向 gh 提供 GitHub Actions 自带令牌；无需新增 PAT。所有验证为离线/模拟账号测试，不代表每位朋友的真实 OAuth 或云端网易云连接都已验收。

## 什么算完成更新

- 提交并 push main。
- 等待 **Build and release macOS installer** 成功，而不只是 Git push 成功。
- 检查 Release 的源码 SHA 与该提交一致、ZIP 和 `.sha256` 两个附件都在。
- 分享该 Release 链接。构建失败时旧包保持可用，但不能声称旧包已包含新代码。

如果依赖准备、测试或打包失败，不会公开新 Release。修复后再 push；临时网络失败也可手动重跑。若草稿上传中断，保留草稿供核查，不会把缺附件的版本自动标为公开。源码快照不是可双击安装包。

## 新用户与老用户

新用户下载新包后跟随原有完整引导，用自己的账号部署当前包内代码。

老用户先在旧安装器点「退出安装助手」，下载并打开新版，然后确认「用此安装包更新云端程序」。不删除配置目录，不重新写入 Secrets，不重新创建歌单，不清空加密状态。升级保留 Git 历史及非托管文件，仅替换托管路径；曾手工修改托管代码的用户应先备份，确认更新意味着接受这些路径被新版替换。

升级验证仓库所有者与安装标记；先暂停新任务并检查所有活动状态，再创建基于当前 main 的普通提交，以非强推更新。并发提交导致非快进时停止，不覆盖对方变更。更新成功后只恢复原来启用的定时，原本暂停则保持暂停；任何中途失败都保留暂停状态并提示重试。代码升级不发起音乐同步，也不能绕过 Spotify 冷却。

版本检查目前通过 Release 和包内界面进行，没有后台静默更新。仅打开新包不会自动修改朋友的 GitHub。
